## scope

Implement only `dev/container-release-template`, using `home-web/scripts/release.sh` and `home-web/docs/releases.md` as read-only references. The template will support container publication, text-only Forgejo releases, and removal of older releases and image package versions after successful publication. Do not modify, install into, migrate, commit in, or publish from any existing project, including `dev-docker`, `home-web`, `yt-web`, `my-library`, `my-rss`, `baikal-docker`, and `ntr-server`. Their future adoption is a separate task. Examples, adapters, fixtures, documentation, and installation/update tools belong entirely inside the new template repository. This planning stage changes only `2-plan.md` under `~/workdir/tasks/1-standardize-container-releases/` and performs no repository creation or remote mutations. This narrowed scope supersedes the earlier seven-project adoption scope in `1-goal.md`; do not change that file as part of this plan update.

## Reference findings

- `home-web/docs/releases.md` specifies clean `main`, the exact `package.json` semantic version, tests and syntax checks, source push, a matching versioned Git tag, and a final registry image published only as `latest`. Node 24 is a requirement of that application, not of the shared engine.
- Its documented token command injects `FORGEJO_TOKEN` for one process; `FORGEJO_USER` defaults to `dev`. Credentials remain outside Git, Compose, shell arguments, and persistent Docker configuration. Temporary authentication excludes inherited credential helpers; Git, API clients, Docker, and builders must trust the registry's TLS configuration.
- Its builder platform preflight runs before project tests, Git fetch/push, registry login, or builds, including recovery. Advertised AMD64/ARM64 capability is not proof of runtime execution. Emulation setup belongs to the host administrator; release tooling must not install binfmt or run privileged setup.
- The current reference exports four archive/checksum attachments and separately rebuilds `latest`. Its `--promote-latest` recovery requires those attachments. The new template must replace these behaviors with attachment-free publication, build-once digest promotion, and identity-based recovery.
- Other projects were inspected only to understand reusable extension needs: package-file versions, explicit tags, `VERSION`, Cargo metadata, project-specific checks, and dependent multi-image suites. These are fixture/example inputs, not authorization to change those projects or port all their release logic now.
- Forgejo package listings contain ordinary tags and `sha256:` versions. The running Forgejo 17 Swagger exposes paginated package/release listing and deletion endpoints. Returned page sizes can be smaller than the requested limit, and deleting digest versions requires manifest-reachability protection.

## Implementation plan

### 1. Create the template repository

- When implementation is authorized, create a local `~/workdir/container-release-template` repository targeting `dev/container-release-template`. Confirm remote visibility and obtain approval before creating or pushing the remote; do not create it during planning.
- Provide `release_template/` for the engine, `scripts/` for entry points and installation/update tools, `examples/` for generic consumer configurations/hooks, `tests/` for isolated fixtures, a template `VERSION`, and dedicated `docs/` files. Use a short README with links and a table of contents for all Markdown headers.
- Use Python 3.11+ standard-library modules for configuration, API calls, state, and tests, with Git and Docker Buildx as external tools. A Bash launcher may provide the familiar `scripts/release.sh` interface. Report missing tools instead of installing system packages or requesting root.
- Separate configuration validation, source identity, registry operations, Forgejo operations, release state, and cleanup. Do not embed seven application-specific release programs or dependencies into the template.
- Keep release identity and cleanup candidate selection independent of CLI, filesystem, Docker, and HTTP details. The workflow coordinates adapters; adapters return validated evidence and apply approved operations rather than implement competing promotion/retention policies.

### 2. Define configuration and extension points

- Define and validate a `release.json` contract with exact Forgejo owner/repository, registry, image allowlist, version source, required platforms, source-push policy, build/verification hooks, and description inputs. No production repository or image is an implicit default.
- Include generic examples for a Node application with package/lockfile version agreement, an explicit semantic tag or `VERSION` file, and an external version-command hook suitable for Cargo metadata. Use synthetic repository names and isolated fixtures rather than copying live credentials or mutable production state.
- Define hook inputs/outputs for source commit, version, platform, dependency references, and verified immutable image identities. Invoke commands as argument arrays with explicit working directories, not interpolated shell strings. Hooks requiring a shell must select it explicitly. Pass credentials only to the operations that need them; support BuildKit secrets without exposing tokens in build arguments or image layers.
- Support a configurable multi-image dependency graph and synthetic parent/child example. Require each child to consume the exact parent built by the same invocation; reject cycles, missing outputs, or ambiguous references. Do not implement or modify the actual `dev-docker` suite in this task.
- Default final registry publication to `latest` only, matching `home-web`; support explicit retained current-version aliases for future consumers without creating them by default. Required platforms are configurable, with an AMD64/ARM64 example rather than an unconditional architecture expansion.
- Use `FORGEJO_USERNAME` as the explicit login name with documented `FORGEJO_USER` compatibility, rejecting conflicting values. Package-owner identity is not a login fallback. Treat the request's `FORFGEJO_TOKEN` spelling as a typo for `FORGEJO_TOKEN`: this variable selects a token-file path, defaulting to `~/.config/forgejo/forgejo-token` when unset. Expand the current user's home directory and read the token from that protected file at runtime; do not treat the path as the token or accept ambiguous raw-token/path autodetection. An explicitly empty value, missing/unreadable file, or empty token must fail clearly without printing its contents. Never persist token contents in configuration, logs, checkpoints, or Git, and never create or modify the user's token file.

### 3. Implement publication and recovery

- Implement checkpointed stages: preflight, project checks, source confirmation, build and verification, image promotion, text-only release publication, final verification, then cleanup. Bind state to source commit, version, validated configuration, and pinned template revision; write credential-free state atomically under an ignored working directory.
- Address review F2 with a versioned checkpoint schema containing a stable run ID, operation IDs, exact staging references, immutable prepared-output evidence, predecessor publication identities, and pending/completed operation records. Persist operation intent before builds or remote writes. Flush checkpoint data, atomically replace the file on the same filesystem, and flush its parent directory before relying on the transition; unsupported durability requirements must fail explicitly.
- Reconcile every pending operation against its exact local/remote identities before retrying. A lost response from a staging push, alias update, Git tag push, or Forgejo release creation must not cause blind repetition, silent overwrite, or duplicate creation. Mark completion only after verification. If a completed build has no recoverable digest evidence, stop for explicit recovery rather than automatically rebuild and claim build-once behavior. Keep prepared outputs distinct from publication progress, and reject unknown checkpoint schema versions.
- Require clean `main`, valid semantic versions, trusted endpoints, and consistent Git tag/source identities. Check configured builder platforms before project tests, Git fetch/push, registry login, or builds in both publication and recovery. Diagnostics name the selected builder, advertised platforms, and required platforms.
- Allow an explicit source-push policy and verify the configured remote source commit before publication. Never force-push, retarget existing Git tags, disable TLS, install emulation, or change host settings. Preserve selected Docker contexts/builders and use isolated temporary authentication without inherited credentials/helpers.
- Build each configured image/platform once, verify outputs and labels, record immutable digests, and promote the verified content without rebuilding. Temporary staging references must be release-unique. For image suites, verify all required images before promotion and keep historical cleanup disabled until every promotion and release verification succeeds.
- Address review F1 with a promotion-eligibility gate before any mutable alias write or Forgejo release publication, including resume. Capture the accepted predecessor release/version/source and every retained alias digest in prepared state. Require a new release to advance the established published semantic version; an equal version is allowed only for an identity-matching resume. Refuse older releases, ambiguous current metadata, or unrelated alias changes before writing any alias. A first publication requires confirmed absence of predecessor records/aliases, not merely missing local state.
- On resume, accept each suite alias only if it still matches this run's recorded predecessor or already matches this run's verified target. Reconcile a mixed predecessor/target suite only when all identities belong to this recorded transition and no newer/conflicting publication exists. Re-read publication/alias evidence before each promotion and release write; a newer successful publication makes an old checkpoint stale even when its Git tag and prepared digests remain valid. Never refresh a stale checkpoint's predecessor automatically. Keep the single-publisher requirement because these checks cannot provide cross-host compare-and-swap.
- Create a Forgejo release tied to the exact versioned Git tag, with description text recording source commit, template revision, image references/digests, platforms, and verification evidence. Upload zero attachments; do not export image archives or require checksums/provenance attachments for publication or recovery.
- Provide identity-based resume/promotion recovery and cleanup-only retry modes. Reconcile saved state with remote images, tags, and release records; reuse only matching identities and reject conflicts. Recovery must not depend on archive assets or rebuild already verified images. Report nontransactional partial publication honestly and never run historical cleanup after publication failure.

### 4. Implement safe cleanup

- Provide a read-only cleanup plan and an apply stage with identical candidate selection. Successful publication may apply cleanup only after final verification; cleanup-only retry must be bound to the same verified release state. Do not run either mode against the seven existing projects as part of template development.
- Collect all package/release pages to exhaustion before deletion, even when a page is shorter than requested. Snapshot candidates before deleting, validate statuses and response shapes, and URL-encode names/versions. Scope package operations to exact configured image names and repository associations, never every package under an owner.
- Protect the new release, retained aliases, index digests, platform manifests, attestations, and nested OCI dependencies. Compute the union of protected content for all configured suite images. Verify Forgejo alias/digest deletion semantics using an authorized disposable Forgejo instance before enabling destructive container cleanup; never assume deleting an old tag cannot affect shared current content.
- Select only provably older eligible versions/releases. Preserve Git tags, source history, drafts, prereleases, unrecognized identities, newer publications, and unrelated packages. Use validated version ordering rather than list position, display names, or timestamps alone. Treat unversioned historical digest records conservatively when their identity/order cannot be proven; report exclusions rather than delete speculatively.
- Revalidate retained release/image identities immediately before cleanup and abort if `latest` changes, a newer publication appears, ownership is unclear, or reachability cannot be verified. Serialize local operations and document the single-publisher requirement across hosts; a local lock is not a distributed transaction.
- Stop on cleanup failure and return nonzero with a distinct “publication succeeded; cleanup incomplete” result. Preserve retry state and remaining candidates without rolling back new content. Accept confirmed target absence on retry, not arbitrary API failures. Verify retained images and platforms after cleanup.
- Address review F3 by recording every temporary tag in the checkpoint with a validated staging namespace, run ID, exact image repository, and expected digest. Retire the successful run's staging aliases only after complete publication verification and only when Forgejo deletion semantics and current manifest reachability prove removal safe. Keep protected digest records even when their staging aliases can be removed; never bypass the existing deletion-evidence gate to achieve latest-only tagging.
- Preserve references needed by unfinished resumable runs. Abandoned-run cleanup is a separate explicit operation using selected run IDs, their verified checkpoint inventories, and a documented retention threshold; neither tag-name pattern nor age alone grants deletion authority. Do not expire active runs automatically. Retain durable staging inventories until all recorded retirement operations finish, resume partial retirement idempotently, and report unsafe/unclassifiable remnants as cleanup incomplete rather than silently leaving permanent staging growth.

### 5. Provide installation and update tooling

- Implement an explicit opt-in installer/updater inside the template repository that vendors a fixed shared-file inventory into a supplied destination's `scripts/release-template/`. Record template version, immutable upstream commit, and file checksums in `release-template.lock.json`; do not fetch or execute mutable remote scripts during consumer releases.
- Add dry-run and managed-file verification modes. Validate the pinned source revision, reject path traversal or writes outside the supplied destination, and refuse locally modified managed files. Keep consumer configuration/hooks outside the managed inventory and produce a reviewable update diff.
- Address review F4 with a destination-scoped lock shared by updater and release startup for the duration of each operation. Before writing, validate the entire old inventory and prepare the new files, checksums, and lock record in a same-filesystem transaction directory. Persist a journal of intended replacements/removals and backups using durable atomic state writes; never modify untracked or user-changed files as part of rollback or recovery.
- Apply managed-file replacements and removals under that lock, retaining a durable in-progress marker. Remove obsolete upstream files only when they belong to the old inventory and still match its checksum. Replace `release-template.lock.json` last, verify the installed inventory, then mark the transaction complete and remove the in-progress marker. Initial installation uses the same protocol with a confirmed empty managed destination.
- After interruption, the updater must detect the journal, distinguish recorded partial writes from user modifications by hashes, and offer deterministic completion or restoration using staged files/backups. Conflicting external changes stop for manual resolution. A stable launcher outside the changing managed inventory must acquire the destination lock and verify the lock/inventory and absence of an incomplete transaction before importing the vendored engine; release startup must never execute a mixed installation. Document and enforce the supported locking/filesystem assumptions rather than claim multi-file replacement is atomic.
- Test installation and updates only against disposable consumer fixtures under approved temporary paths. Do not run tooling against any existing project or add files, wrappers, locks, versions, configuration, or documentation to those projects. Deliver future adoption instructions inside the template repository only.

### 6. Test and document the template

- Use Python standard-library tests, disposable Git repositories, fake Docker commands, and local Forgejo/OCI fixtures. Permit loopback HTTP only through explicit test configuration; never load production credentials or mutate production content from tests.
- Test invalid configuration/version sources, dirty/non-main checkouts, source drift, Git conflicts, preflight ordering in normal/recovery modes, unsupported platforms, TLS/auth failures, username compatibility/conflicts, token redaction, temporary credential isolation, and unchanged builder/context selection.
- Test the unset `FORGEJO_TOKEN` default using a disposable home directory, explicit token-file overrides, quoted `~` expansion, explicit empty values, missing/unreadable/empty files, and redaction. No test may read the real `~/.config/forgejo/forgejo-token`. Document `FORGEJO_TOKEN` as a file-path setting rather than the raw-token injection used by the read-only `home-web` reference.
- Test build-once promotion, text-only release publication with zero asset uploads, digest-bound resume, conflicting remote identities, all publication failure boundaries, multi-image dependency ordering, and partial suite promotion. Assert no historical deletions before complete verification.
- For F1, resume an older interrupted checkpoint after a newer successful publication and assert zero alias writes, release publication writes, and historical deletions. Include mixed suite aliases, equal-version matching resume, conflicting equal versions, unknown predecessor metadata, and first-publication absence checks. Assert the eligibility gate runs before the first mutable write and repeats before subsequent writes.
- For F2, inject process termination and server-accepted/lost-response faults between intent persistence, each build/push/tag/release write, verification, and completion persistence. Verify restart reconciliation against the same operation/staging identities, no blind duplicate writes or rebuilds, rejection of unknown schemas, and explicit recovery when prepared image evidence cannot be reconstructed.
- Test server-capped pagination, nested indexes, attestations, shared manifests, `sha256:` package versions, old aliases sharing a current digest, unrelated repositories, ambiguous/newer versions, drafts/prereleases, concurrent `latest` changes, partial cleanup, and idempotent cleanup-only retry.
- For F3, run repeated successful synthetic releases and verify safe retirement of successful-run staging aliases without removing current manifests. Interrupt another run and verify its resumable references survive. Exercise partial staging retirement, missing inventories, ownership/digest conflicts, explicit abandoned-run selection, retention thresholds, and fail-closed behavior when live deletion evidence is unavailable.
- Test pinned installation/update inventories, checksum mismatches, missing or modified managed files, destination/path safety, dry-run behavior, and preservation of fixture hooks/configuration. No test destination may be one of the existing seven projects.
- For F4, interrupt after each managed-file replacement/removal, lock replacement, and transaction-completion boundary. Restart and verify deterministic completion/restoration without overwriting user changes; test upstream file removal, initial-install interruption, concurrent update/update and update/release attempts, and release refusal before engine import when inventory or transaction state is inconsistent. Use disposable destinations only.
- Add dedicated documentation for configuration/hooks, credentials/CA trust, publication/recovery, retention safety, and installation/updates. Document Python/tool requirements, `latest`-only defaults, administrator-owned emulation setup, single-publisher limits, and loss of historical package rollback after cleanup. Explain which `home-web` conventions are preserved and why archive-based publication/recovery is replaced. Do not edit `home-web/docs/releases.md` itself.

## Acceptance criteria

- Only the new `dev/container-release-template` repository receives implementation changes. All seven existing projects remain untouched, with adoption deferred to a separate task.
- The template includes a reusable release engine, validated configuration/hooks, synthetic single/multi-image examples, tests, documentation, and explicit pinned installation/update tools exercised only against disposable fixtures.
- Its reference configuration preserves clean-main/version/source guarantees, early builder-platform checks, trusted TLS, isolated credentials, `FORGEJO_USER` compatibility, versioned Git tags, and `latest`-only final registry publication without imposing Node on the shared engine.
- With `FORGEJO_TOKEN` unset, the template reads credentials from `~/.config/forgejo/forgejo-token`; setting it overrides the file path. Token contents never appear in command arguments, logs, persisted release state, or Git, and the existing token file remains unchanged.
- Publication builds verified images once, creates description-only Forgejo releases with zero attachments, and resumes from immutable identities without archive-dependent checks or rebuilds.
- Stale checkpoints cannot move `latest` backward or publish an older conflicting release; promotion eligibility is verified before mutable writes. Matching partial suite transitions remain resumable without accepting unrelated/newer publication state.
- Durable intent and checkpoint reconciliation handle process kills and lost responses without blind duplicate publication or rebuilds. Missing immutable build evidence stops for explicit recovery rather than weakening the build-once contract.
- Cleanup runs only after complete publication verification, protects retained aliases and reachable manifests, preserves Git tags/unrelated or uncertain records, and reports failures with retryable state.
- Successful-run staging aliases have an explicit, tested retirement lifecycle; unfinished runs retain their required references, and abandoned-run cleanup requires bounded explicit selection and verified ownership/reachability.
- Installation/update interruption cannot cause a release to execute mixed managed versions. Lock-last updates, journal-based recovery, obsolete-file handling, and shared updater/release locking preserve fixture user files and hooks.
- Tests cover pagination, shared digests, multi-image failures, concurrency detection, publication/recovery, and update safety. Live deletion semantics must be proven in an authorized disposable environment before destructive container cleanup is enabled.
- No existing project is migrated, used as an installation destination, released, pushed, or cleaned up. Planning itself changes only this plan file.

## Risks and decisions

- Repository target is `dev/container-release-template`; remote visibility and remote creation/push still require approval. This plan does not authorize modifications to existing projects.
- Read-only references inform a reusable contract, not a requirement to port every project's tooling. Application-specific runtime validation and actual seven-project integration belong to later adoption tasks.
- Vendored pinned files provide explicit, reviewable updates; a Forgejo repository template alone cannot propagate fixes to existing consumers. Installer/updater availability is in scope, executing it against existing projects is not.
- `home-web` provides safety and operator conventions, not its attachment contract or duplicate builds. The default publishes only `latest` as a final registry alias, with versioned Git tags kept separately.
- Forgejo digest deletion can invalidate retained multi-platform content. Fail closed when deletion semantics, manifest reachability, version ordering, or ownership are uncertain, even if some historical content must remain.
- Publication and cleanup are nontransactional across Git, Forgejo, and registry operations. Require a single publisher, detect identity changes, retain recovery state, and never claim a local lock eliminates cross-host races.
- The goal still records the original broader adoption request. This plan follows the user's latest template-only scope; updating the goal or planning adoption is separate work.
