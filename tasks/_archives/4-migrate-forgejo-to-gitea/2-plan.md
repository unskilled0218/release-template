## Scope

Migrate this container release template from Forgejo to Gitea across active runtime code, configuration/credentials, API fixtures, retention verification, examples, and documentation. Use provider-neutral `GIT_*` credential settings, not `GITEA_*` or `FORGEJO_*`. Preserve build-once publication, text-only releases, immutable checkpoint identity, complete survivor protection, and dependency-safe retirement. Use an explicit breaking contract migration rather than silent legacy fallback or a new multi-provider framework. Historical task archives and health-history records remain historical. This stage writes only this plan and commits it; no implementation changes, credential access, deployment probing, live mutation, consumer migration, or remote reconfiguration is authorized.

## Compatibility findings

- Active Forgejo coupling is in the configuration key `forgejo`, the `Forgejo` adapter and workflow/cleanup attributes, credential variables/default path, release-description wording, test fixtures, examples, and documentation. `Runner` currently removes only `FORGEJO_*` credential settings from subprocess environments.
- The destructive gate is product-specific, not merely branding: `cleanup.deletion_evidence()` accepts schema 1 with `server_major: 17`, and `deletion_environment()` uses a `17.` prefix. A Gitea migration must not change that prefix to a broad new major and treat old server/storage evidence as valid.
- Official [API usage](https://docs.gitea.com/development/api-usage/) documentation confirms `Authorization: token ...` for personal access tokens and `page`/`limit` pagination with server-configurable caps. Preserve header authentication, exhaustive pagination, and bounded error handling; do not move secrets into query strings.
- The public [Gitea OpenAPI document](https://gitea.com/swagger.v1.json), inspected during planning, exposes `/api/v1/version`, repository release listing/creation/lookup/deletion, and owner-scoped package listing/lookup/version deletion using the paths already employed by the adapter. Release creation uses `tag_name`, `target_commitish`, `name`, `body`, `draft`, and `prerelease`; documented success codes are 201 for creation and 204 for deletion, with 404 for missing targets. Package records expose `type`, `name`, `version`, and a repository association. Server version is a string field named `version`.
- That public Swagger identified itself as `29.0.0+dev-160-g55186ca39b`; it is a mutable development reference, not the user's deployment. The installed Gitea version and its exact Swagger/storage behavior are unknown. Do not infer compatibility or enable cleanup based on this public version, an assumed `1.x` range, or any major-only comparison.
- Gitea's [container registry](https://docs.gitea.com/usage/packages/container/) documents OCI-compatible images named `{registry}/{owner}/{image}` and case-insensitive tags. Existing lowercase image/tag generation and same-origin registry authentication can remain. The [package overview](https://docs.gitea.com/usage/packages/overview/) states that packages belong to owners, not repositories, and repository linking affects the whole package. A push does not establish repository-scoped deletion authority; missing or foreign links must remain protected and visible as incomplete cleanup.
- Existing checkpoints bind both the template revision and the canonical configuration digest. Renaming configuration fields or upgrading the template must not rewrite these identities to force old runs to resume.

## Implementation Plan

### 1. Define the Gitea configuration and credential contract

- Introduce consumer configuration schema 2 with required `gitea` HTTPS origin instead of `forgejo`. Keep the remaining repository, registry, version, image, hook, secret, and source-push semantics unchanged. Retain exact origin/registry agreement, explicit owner/repository selection, trusted TLS, and test-only loopback restrictions.
- Reject schema-1 Forgejo configurations, any retired `forgejo` key, and mixed old/new origin keys with an actionable migration error before credentials or network clients are used. Do not silently normalize old configuration or accept ambiguous dual-provider input. Update every example to schema 2 with synthetic `gitea.example.invalid` endpoints.
- Use `GIT_TOKEN` exclusively as a token-file-path override, defaulting to `~/.config/gitea/gitea-token` when unset. Preserve current-user home expansion, ownership/private-mode/readability checks, nonempty single-token validation, explicit-empty rejection, and the prohibition on raw-token/path autodetection. Never create, copy, move, rewrite, or inspect the user's actual credential files during implementation.
- Use only `GIT_USERNAME` as the explicit account login, not `GIT_USER` or another alias. Missing or explicitly empty login values fail clearly. This custom release-tool setting selects the authentication account, not Git commit author identity. Never infer login from the package/repository owner.
- Reject unsupported `GIT_USER`, `GITEA_TOKEN`, `GITEA_USERNAME`, `GITEA_USER`, `FORGEJO_TOKEN`, `FORGEJO_USERNAME`, and `FORGEJO_USER` with a bounded migration error if present, including empty values, before token-file access. Do not accept them as aliases, fall back to them, or search the old default credential path. Operators can explicitly choose an existing protected file through `GIT_TOKEN` only when it contains a valid Gitea token; the tool performs no secret migration.
- Strip the exact supported credential names `GIT_TOKEN` and `GIT_USERNAME`, plus the unsupported names listed above, from `Runner` subprocess environments, even when testing the runner directly. Do not blanket-strip `GIT_*`: preserve unrelated native Git settings such as `GIT_SSH_COMMAND` and author/committer identity variables. Test both credential isolation and preservation of native Git settings. Keep token stdin for Docker login, private temporary authentication, stdout redaction, bounded command failures, and selected builder/context behavior unchanged. Credential-free `validate` still does not read token files or require a login.

### 2. Migrate the service adapter and its callers

- Rename `Forgejo` to `Gitea` in `release_template/adapters.py` and update CLI construction, workflow arguments/attributes, cleanup calls, fixtures, and tests consistently. Use `config["gitea"]` for HTTP clients, Git destination validation, OCI source URLs, and historical digest source checks. Do not leave a silently usable Forgejo adapter alias or introduce provider plugins.
- Retain the documented Gitea `/api/v1` release/package paths, URL encoding, exact status handling, JSON payloads, header token authentication, and pagination-to-exhaustion behavior where contract tests confirm compatibility. Keep 401/403/connectivity failures distinct from 404 absence. Add loopback request/response assertions for Gitea release POST/GET/DELETE, package GET/DELETE, version responses, capped/repeated pages, and malformed records rather than only renaming mocks.
- Preserve OCI digest checks, complete runnable-platform classification, source/version/revision labels, same-origin Bearer challenge restrictions, and redirect refusal. No Git destination or remote URL is changed by this task, and no real publication, tag push, registry login, or build is run during implementation.
- Preserve repository association as an additional deletion boundary on owner-scoped packages. Same-name packages with missing or foreign repository association contribute full survivor graph protection, are never auto-linked/reassigned/deleted, and receive explicit skipped reasons so cleanup cannot report complete while configured package retirement was withheld. Keep unrelated image names outside deletion authority.
- Document that linking is an operator-controlled, whole-package action requiring separate consumer adoption approval. Do not add automatic link API calls or infer ownership from image name, push success, labels alone, or repository existence. Tests must include null/missing links, foreign links, and the exact matching association needed for a positive cleanup case.
- Change new release-description prose and active diagnostics to Gitea terminology. Keep the established release identity marker and structured publication schema stable so recognized imported release metadata remains readable; do not alter already published descriptions or weaken predecessor/alias matching.

### 3. Replace Forgejo deletion evidence with Gitea verification

- Introduce deletion-evidence schema 2, requiring `product: "gitea"`, the exact configured `origin`, an exact `server_version`, a distinct disposable repository, nonempty operator/verification metadata, and the existing true results for alias preservation, scoped digest deletion, and retained platform pullability. Preserve the trusted-operator-input model; this is not cryptographic proof or automatic product detection.
- Reject every schema-1 Forgejo attestation and major-only record, even if its origin matches the new host or its booleans are true. Do not convert, auto-upgrade, or manufacture evidence from mock tests. Missing, malformed, mixed-product, or stale evidence keeps all destructive cleanup disabled.
- Replace the `17.` runtime check with validation of the Gitea `/api/v1/version` response and exact equality with attested `server_version`. Require bounded full `MAJOR.MINOR.PATCH` syntax with optional prerelease/build suffixes and preserve the exact original string. Reject major-only strings such as `17`, whitespace/control characters, and malformed versions in both evidence and runtime responses. Use a dedicated server-version validator rather than the release-only parser; do not strip suffixes or use prefix/major-only matching. Malformed, unavailable, unauthorized, or non-matching responses stop before DELETE.
- Apply this same gate to normal post-publication cleanup, cleanup-only retry, and explicit abandoned-run retirement. Publication without deletion evidence may still complete and remain recorded as successful, followed by the existing nonzero cleanup-incomplete result. Do not weaken dependency order, retirement fingerprints, fresh survivor checks, or absence reconciliation to make the migration pass.
- Update disposable fixture evidence/version responses to Gitea schema 2. Cover exact full-version matches and mismatches, including an older `1.x`-style version and a newer multi-digit major/build-suffixed version, without claiming a supported deployment range from those fixtures. Forgejo schema 1, `server_major: 17`, wrong product/origin, same disposable/production repository, missing fields, and API failures must all produce zero deletions.
- Update the live verification procedure to require separately authorized tests on the actual Gitea deployment and exact version/storage environment: alias/digest semantics, nested/shared manifests, pullability, owner/repository linkage, dependency-safe cleanup interruption/retry, and text-only releases. Neither public API documentation nor local tests satisfies this gate. The `/version` string alone cannot establish product identity; the operator must attest the actual tested Gitea environment.

### 4. Preserve checkpoint and publication identities

- Keep outer checkpoint schema, exact template/source/configuration identity matching, durable state writes, operation IDs, and nested retirement metadata unchanged. The schema-2 configuration intentionally changes the canonical config hash, and a new template pin changes its revision; old checkpoints must fail identity checks rather than be rewritten or silently adopted.
- Add explicit tests for schema-1 configuration rejection before remote operations and old-pin/old-config checkpoint refusal under the new contract. Verify unchanged checkpoint bytes, zero alias/release/package mutations, and no registry login on rejection. Test same-revision, schema-2 Gitea publish/resume/cleanup behavior separately.
- Preserve old checkpoints, release identity metadata, retirement schedules, and provenance for separately reviewed handling. No cross-revision migration command, automatic state deletion, forced source rollback, or vulnerable old-code cleanup workaround is introduced. A renamed server alone does not establish that remote package aliases, source commits, or imported releases match previous identities.
- Keep existing recognized release metadata parsing and forward-version checks intact. New Gitea publication still needs exact current Git destination/source, image identities, predecessor records, and aliases. Unknown migrated records/aliases remain an explicit adoption problem, not an excuse to bypass first-publication or stale-resume checks.
- Leave stable bootstrap bytes and the managed-installation protocol unchanged so code updates continue through the existing pinned installer. Test installation of the renamed engine and schema-2 validation in disposable consumers without modifying any existing project.

### 5. Update examples documentation and regression fixtures

Retain the short README and dedicated-topic structure. Add a dedicated `docs/gitea-migration.md` with its own table of contents and link it from README and installation/credentials documentation.
- Document the breaking schema/key/environment/default-path changes with before/after examples using only `GIT_TOKEN` and `GIT_USERNAME`, explicit rejection of `GIT_USER` and both provider-specific credential prefixes, safe operator-managed token selection, and no credential-file copying by the tool. Explain that package permissions are owner-scoped and repository linking is whole-package. Describe required Gitea repository/package token scopes, checking any additional read scope needed by the deployed version, without recommending blanket admin access or creating tokens automatically.
- Document fresh Gitea-only evidence, full-version binding, unchanged disabled-by-default deletion, checkpoint incompatibility, and deferred live/consumer adoption. Distinguish documented/public API compatibility from actual deployed-server verification. Mark earlier Forgejo verification statements as historical rather than retroactively claiming they verified Gitea. Preserve the existing single-publisher, trusted TLS, explicit BuildKit-secret, unsupported external-redirect, and durability limitations.
- Rename `FakeForgejo` and `RemovalForgejo`, fixture endpoints/default homes, injected CLI patch names, workflow test attributes, and evidence helpers consistently. Keep realistic loopback OCI behavior and the removal-aware fixture: deleted dependencies must remain absent. Add focused config/credential/Gitea API/evidence migration tests while retaining every existing safety scenario.
- Do not bulk-rewrite `tasks/_archives/`, prior health-history records, Git history, or old task evidence. Expected remaining Forgejo references are limited to historical artifacts, this task's migration context, retired-input rejection code/tests, and the explicit migration guide. Scan active implementation/examples/docs for stale operative Forgejo settings, rather than demanding an indiscriminate zero-match grep.

- Run focused migration tests, then `TMPDIR=/tmp/opencode python3 -B -m unittest discover -s tests`, `bash -n scripts/release.sh`, schema-2 credential-free validation for all five examples, Python syntax/version checks, Markdown table-of-contents/link checks for changed docs, and `git diff --check`. The preceding reviewed baseline is 110 tests; do not drop safety cases just to make renamed fixtures pass.
- Verify that positive adapter tests execute real Gitea-shaped HTTP responses for the used endpoints, not just renamed in-process mocks. Confirm all negative evidence/identity cases produce zero destructive or publication writes as appropriate. Verify supported `GIT_*` credential settings and rejected provider-specific names cannot leak through subprocess environments/logs/checkpoints, while unrelated native Git variables remain available.
- Record changes, actual results, breaking migration decisions, and remaining target-version/live-verification limits in this task's `4-implemented.md` when implementation is authorized. Use the new task-named implementation branch and commit only scoped changes. Do not push, change remotes, probe the private deployment, publish releases, migrate consumers, or modify token files without a separate request.

## Acceptance Criteria

- Active configuration/examples use schema 2 and `gitea`; schema-1, legacy-only, and mixed origin keys fail clearly before credentials/network use. Runtime adapters/callers and new publication text use Gitea terminology without a new provider framework.
- The only supported credential settings are `GIT_TOKEN` for the token-file path and `GIT_USERNAME` for explicit login. File protection, missing/empty settings, and unsupported-variable rejection are documented and tested. `GIT_USER`, `GITEA_*`, and `FORGEJO_*` credential settings are rejected, not aliases. Exact credential names are isolated from hook/tool environments without stripping unrelated native `GIT_*` variables, and no actual token file is read or changed by tests.
- Loopback contracts verify the documented Gitea release/package/version API paths, payloads, statuses, pagination, and error distinctions. Missing/foreign package repository links remain protected and report cleanup incomplete; the tool never auto-links a package.
- Only fresh schema-2, product-bound, origin-bound, exact-full-version Gitea deletion evidence can enable destructive operations. Old Forgejo evidence, major-only checks, malformed responses, version drift, and absent evidence cause zero deletions. Local fixtures never become production attestations.
- Existing checkpoint identity guards, release metadata parsing, forward-only publication, build-once recovery, all-runnable platform checks, complete survivor protection, durable retirement order, and absence reconciliation remain intact. Old configuration/template checkpoints are refused without mutation; same-revision Gitea cases pass.
- Bootstrap/update behavior and fixture-only consumer installation remain covered. Historical task archives, prior health records, unrelated files, private credentials, Git remotes, and actual consumers remain untouched.
- The full suite and static/example/documentation checks pass, and version statements agree on `0.2.0`. Documentation clearly separates implemented API contracts from unverified deployed Gitea behavior; live deletion remains gated pending separately approved same-server checks.

## Risks And Decisions

- This is a Gitea-only service contract cutover with provider-neutral `GIT_*` credential names, not indefinite dual Forgejo/Gitea support. Both provider-specific credential prefixes are rejected. Explicit rejection plus a migration guide is safer than silently reusing old origins or credentials. The version/schema bumps make the break visible.
- The user's installed version, token setup, import history, and Gitea package linkage are unknown. Public Swagger was a development build; use it only to identify documented endpoint shapes, not as evidence about the private deployment or deletion semantics.
- Exact version strings can change after patch/build upgrades. Reverification is intentional; matching a broad major or truncating build metadata would overstate old deletion evidence. An attestation remains trusted operator input, not automatic platform identification.
- Gitea package association is a whole-package operation under an owner-scoped permission model. Do not auto-reassign packages or relax repository checks to hide missing linkage, even if that leaves cleanup incomplete until explicit adoption work.
- Changing config keys/pins intentionally prevents old checkpoint reuse. Stable publication metadata stays readable, but no automatic identity migration is offered. Keep original state/provenance for separately reviewed recovery.
- Preserve historical artifacts as evidence of what actually ran against Forgejo. Relevant active text must be updated without falsifying prior reviews, attestations, or implementation records.
