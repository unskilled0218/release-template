## Scope

Publish reusable AMD64/ARM64 images to Gitea Packages, link the configured image packages to their repository so they appear in its Packages tab, remove task-owned local release images after successful verification, and make the release description a human-readable account of the project's update: features, fixes, compatibility changes, and relevant upgrade notes. The user's clarifications supersede the earlier image-focused description and exclusion of package linking. Do not turn release descriptions into image catalogs, pull/run instructions, provenance dumps, or another machine-oriented format. Keep image consumption instructions in dedicated documentation.

Task 8 already published and executed `git.lan/dev/container-release-template-hello:latest` on both platforms. Treat `git.lan/dev/example-image:latest` as illustrative, not permission to rename/reassign an owner-scoped package. Preserve the existing configured name unless the user explicitly selects another. This planning update changes only the plan; it accesses no credentials and performs no implementation or remote operations.

After the user's separate request to show the image in this repository's Packages tab, the existing `container-release-template-hello` package was linked to `dev/container-release-template`. All four listed versions were confirmed linked and `latest` retained its digest. This plan adds repeatable engine support for the same explicit operation; the earlier task 8 missing-link evidence remains a historical snapshot, not the current association state.

## Implementation Plan

### 1. Use project-update release notes

- Add an explicit `release_notes` relative-file setting to consumer configuration. Validate its path using existing traversal/symlink safeguards. Require this input for new publication under the updated engine, with a clear migration error when absent; do not silently fall back to image-centered generic text. Keep read-only configuration validation free of credentials and remote calls.
- Store this project's next notes in `docs/releases/0.2.4.md` and point the Ubuntu release configuration at that file. Write concise, curated Markdown describing the actual changes in this release, such as project-focused release notes, backward-reading compatibility, and separately documented image usage. Do not invent features or use unreviewed commit subjects as finished prose.
- Update the bundled example configurations and test configuration fixtures for the new notes input. Consumer examples must explain that their notes belong to the consuming project; do not silently publish this template's update text for another application. Keep generic and Ubuntu example validation usable within this repository.
- Require a version heading matching the requested release, for example `# Release v0.2.4`, followed by useful project-update sections. Include a table of contents for headings. Omit empty sections, decorative tables, emoji, image/platform inventories, generated Docker commands, digest lists, and source/template commit footers.
- Read the note content from the captured Git commit, not an ignored file or mutable working-tree copy. Require a regular committed UTF-8 file with bounded size, for example 64 KiB, and validate it before creating remote publication side effects. Freeze the exact normalized text and its digest for this run; retries must not silently consume later edits.
- The public body is that project-update Markdown alone. Do not append JSON, YAML, XML, hidden HTML metadata, an encoded identity, or an image usage section. The release title/tag identifies the version; the description explains what changed in the project.

### 2. Separate verification identity from the description

- Stop parsing normal release descriptions to recover image/publication identity. Store machine identity in the annotated Git release tag's message instead, outside the Gitea description. This uses an existing immutable, independently verifiable source reference without creating a release attachment, external database, or registry-specific metadata service.
- Define a versioned annotated-tag message envelope with an explicit marker and canonical identity. Use identity schema 2, retaining version, tag, source commit, template revision, repository, targets, and platforms, and adding the committed notes path and normalized-text digest. Machine serialization is permitted in this internal tag record, never in the release description. Keep configuration schema 2 and checkpoint/retirement schemas unchanged; document stricter configuration and the new publication identity format.
- Add small Git adapter helpers to resolve a remote tag's advertised object ID and peeled source commit, fetch the exact tag object without modifying the worktree or replacing local tags, and inspect its type, target, declared tag name, and message. Use normal Git object verification and bounded subprocesses; do not infer identity from a mutable branch name or `target_commitish` string.
- Validate the envelope schema and complete identity: version/tag agreement, repository, source/template revisions, SHA-256 image digests, alias/image/platform coverage, notes path, and notes digest. Require the annotation to target the recorded source commit directly, the peeled commit to agree, and the declared tag name to match the requested release. Authentication, fetch, malformed-object, and missing-required-identity failures must stop progress rather than become absence.
- Keep pure identity validation in policy code and Git/network I/O in adapters. Resolve accepted release identities in workflow orchestration instead of letting `policy.py` fetch network data. Select/validate the highest stable published release before resolving its tag; preserve rejection of unknown publication identities.
- Verify the public description against the note file at the identity's captured source commit and its stored digest. This verifies the intended project text without scraping prose for image metadata. Normalize only explicitly defined line endings and the final newline; arbitrary body changes remain conflicts rather than being ignored.

### 3. Integrate durable publication and legacy compatibility

- Replace new-body rendering in `Workflow.publish` with the frozen committed notes. `release_identity()` emits schema 2 including the notes binding. Preserve default multi-platform build, complete platform/label verification, prepared-digest promotion, optional version aliases, source checks, text-only/non-draft/non-prerelease releases, and asset prohibition.
- After all prepared image outputs exist, create the annotated source tag with the final identity. Persist the exact tag object ID and intended identity before its remote push. Push that captured object without force. On restart, validate/reuse an existing matching local tag and recorded object rather than regenerating a different annotation or replacing tags.
- Reconcile both the remote tag object and complete identity after a lost push response. An existing tag with a conflicting object/identity, a lightweight tag for a new-format release, or a mismatched commit must stop. Do not attach metadata to a pre-existing conflicting tag or rebuild images to escape the conflict.
- Persist the exact project-update body in release intent before POST. Existing-release reconciliation and `verify_publication` compare the schema-2 tag identity, frozen note text/digest, source tag, final aliases, and full runnable evidence. Same-pin retry must not rebuild, repromote unchanged aliases, duplicate a release, or silently PATCH an edited description.
- Preserve a read-only legacy path for schema-1 JSON-backed releases such as live `v0.2.3`, whose tag is lightweight. Resolve and verify their source tag and recognized old body, while new releases use the annotation. A present but malformed new-format tag must never fall back to old JSON and gain authority. Unknown or missing identity remains a failure.
- Allow a recognized legacy predecessor followed by a newer annotated-tag/project-notes release. Do not rewrite the legacy body, move old source tags, update old checkpoint identities, or automatically adopt an old-pin transaction. New binaries can read both generations; old JSON-only binaries may reject new releases and this limitation must be documented.
- Update test fakes to represent annotated tag objects, peeled commits, explicit notes files/content, and release bodies. Preserve genuine static legacy fixtures rather than generating old-format samples through the new renderer. Package association changes are restricted to the explicit opt-in step below; visibility, retention ordering, and deletion gates remain unchanged.

### 4. Link image packages to the repository

- Add a boolean `link_packages` configuration setting, defaulting to false for existing consumers. Set it to true in the approved Ubuntu fixture configuration. This setting explicitly authorizes linking each configured owner-scoped image package to the configured repository, including all its versions; it is not authorization to reassign a foreign-linked package, change visibility, or delete anything. Document the whole-package effect before consumers enable it.
- Add a narrow `Gitea.link_package(name)` adapter using the deployed contract already inspected on Gitea 28.2.0: `POST /api/v1/packages/{owner}/container/{name}/-/link/{repo_name}`, expecting HTTP 201. Encode each path segment independently, derive owner/repository name from validated configuration, and never accept an arbitrary destination supplied by a remote package record. Preserve bounded error messages and TLS/credential isolation.
- With opt-in enabled, inspect the complete paginated inventory and required scoped lookups for each exact configured image name after all prepared outputs pass verification. Validate container type, expected owner/name, and current association. Already matching links need no POST. An explicitly unlinked package may be linked under this approval; foreign links, malformed or uncertain association evidence, lookup/auth failures, or unexpected missing prepared packages stop without reassignment. Do not infer authority from matching image labels alone.
- Perform linking before source-tag push, final alias promotion, and release creation. Persist a `link:<image>` operation intent with owner, image name, target repository, and prepared digest before POST. This keeps a linking failure distinct from completed publication while retaining verified staging outputs for retry. Do not change configuration or publication identity mid-run to bypass a failure.
- After POST, re-read the package association and confirm the intended repository before completing the operation. Preserve registry digests and existing aliases. A successful response with absent, malformed, foreign, or unavailable confirmation leaves linking incomplete and stops later publication stages; it must not be treated as confirmed UI visibility.
- On retry, inspect fresh association evidence first. A confirmed matching link completes pending intent without another POST. Repeating an unconfirmed idempotent link is allowed only after fresh validation still proves the approved unlinked target; never unlink first, force a foreign reassignment, or repeatedly POST through uncertain evidence. Prepared images are reused rather than rebuilt.
- Include association verification in final publication checks when opt-in is enabled, so a later foreign/missing link cannot silently satisfy a claimed linked publication. When disabled, retain existing behavior: publication can remain registry-usable while missing/foreign associations protect content and appear in cleanup diagnostics.
- Linking may make records eligible for existing repository-ownership checks, but does not grant deletion authority. Keep disposable-test evidence gating, survivor graph protection, version eligibility, and raw-digest retirement checks unchanged. No cleanup attestation is created from successful linking.

### 5. Remove local release images after verification

- Add a boolean `remove_local_images` setting, defaulting to false for existing consumers, and enable it in the approved Ubuntu fixture. This explicitly opts the selected release into local image removal after verified publication. It does not authorize remote image/package deletion, broad cache pruning, or removal of unrelated/pre-existing images.
- Before a publish/resume invocation pulls or builds images, capture the selected Docker daemon/context and an ownership baseline for local references/image IDs relevant to the exact configured image names. Record the task-created/pulled release references and immutable digests as they become known. Do not claim ownership merely from a name prefix, label, or a successful release.
- Limit removal to new local references owned by the release run, such as its staging, final alias, or immutable pull references when actually present locally and still matching the recorded digest/image identity. Skip pre-existing references/IDs, unrelated repository tags sharing content, base images such as `ubuntu:24.04`, references changed by another writer, and images used by any running or stopped container. Keep an explicit skipped reason rather than forcing deletion.
- Use exact-reference `docker image rm` operations without `--force`. Do not use image/system/builder prune, blanket dangling-image deletion, recursive cache removal, `docker rmi` over all image IDs, container deletion, or any Gitea/registry DELETE call. Remove only from the originally selected daemon/context; do not iterate all contexts or remote builder caches.
- Start removal only after publication has been independently verified for this invocation and needed runtime checks have finished. Never remove potentially useful images after a failed/incomplete publication or before prepared-output verification. Preserve checkpoints, build metadata, operation evidence, Git source/tags, registry images, and package associations.
- Integrate this finalization into `publish` and `resume`, not `validate`, `cleanup-plan`, or other read-only modes. A verified publication followed by deliberately blocked remote cleanup still qualifies for local image removal: the missing deletion attestation governs remote deletion, not task-owned local copies. Do not let the existing nonzero cleanup exit skip safe local finalization.
- Keep local cleanup outcome separate from publication and remote cleanup. Report removed, already absent, safely skipped, and failed references explicitly. A local removal failure must not invalidate recorded publication, overwrite the original remote-cleanup diagnostic, trigger another build/release, or enable remote deletion; return a clear incomplete-local-cleanup diagnostic when appropriate.
- Make the helper idempotent using fresh local evidence. Confirm already-absent references through a successful inventory/query rather than treating daemon, authentication, permission, or transport errors as absence. Recheck identity and container/shared-reference safety immediately before each removal. Retrying local finalization must not require changing the publication's immutable checkpoint identity.
- Independent live verification may pull images again after the release command. Track those pulls with the same provenance rules and invoke guarded local finalization after the last runtime/retry check as well. Do not claim local images were removed while leaving newly pulled task-owned copies behind. Any pre-existing, shared, or in-use images left intentionally must be listed in results.

## Acceptance Criteria

- AMD64 and ARM64 images remain usable through a documented full `latest` reference, with verified platform selection and default runtime output. With `link_packages: true`, configured packages are confirmed linked to the intended repository and appear in its Packages tab. No unapproved rename, foreign reassignment, or visibility change occurs.
- The release description contains curated human-readable project updates only. It is not an image catalog, Docker usage guide, provenance dump, or serialized/hidden metadata container.
- New identity is verified from a source-bound annotated tag and the committed notes digest, not extracted from project prose. Missing/conflicting/malformed identity or edited notes fails closed; legacy predecessors remain readable without automatic migration.
- Durable tag/release intent, immutable source/object identity, equal/stale-version checks, platform/digest verification, exact-pin refusal, and lost-response recovery remain intact. Retry causes no rebuild, unnecessary promotion, duplicate release, force tag update, or silent description edit.
- Releases remain text-only and asset-free. Historical tags/checkpoints are preserved. Linking is explicit, durable, confirmed, and retry-safe; already correct associations need no new POST, and uncertain/foreign links cannot trigger later publication writes. Deletion safety rules remain unchanged.
- After verified release/runtime checks, opted-in task-owned local image references are removed without force or broad pruning. Pre-existing, base, shared, changed, or container-used images are protected and reported. No local image removal occurs on failed publication or read-only modes; remote packages/images, checkpoints, and evidence remain intact.
- Local regressions and docs/version checks pass. Approved live results separately verify project-focused notes, package pullability, both runtimes, and retry; blocked/unexercised results remain explicit.

## Risks And Decisions

- This is a deliberate change from the earlier image-focused plan. Reading machine identity from a release body would keep forcing artifact fields into prose, so verification moves to annotated Git tags. Canonical machine data remains internal to tag storage and must never be copied into the public description.
- Annotated tags are a format change: new publications require the new envelope, while legacy lightweight tags are accepted only with recognized old metadata. Distinguish missing legacy data from malformed new data and never downgrade after a new-format validation failure.
- Identity schema 2 binds the notes path/hash while retaining image ownership information outside prose. A required `release_notes` setting is a documented stricter publication contract despite unchanged configuration schema. Old consumers must add committed project notes before publishing with the new pin.
- Human text is curated, not automatically invented from image labels or commit subjects. It is frozen by the captured source and note digest; manual edits to a published description become explicit conflicts, not automatic permission to rewrite state.
- Git tags can be force-moved by external actors. This tool never force-updates them, records exact object identity for retries, and verifies remote evidence, but operational serialization and trusted repository permissions remain required.
- Gitea Packages are owner-scoped, and a repository link affects all versions of that package. The user has requested this association, so the approved fixture opts in; other consumers must enable it explicitly. Successful registry pulls alone still do not authorize arbitrary linking, foreign reassignment, or deletion. Keep image usage, project-update prose, repository association, and cleanup authority separate.
- Linking introduces a new pre-publication permission boundary and can alter cleanup ownership eligibility. Treat it as a durable operation with confirmed outcome, never as automatic adoption or as evidence that deletion is safe. Existing correctly linked packages are verified rather than mutated again.
- Local Docker storage may be shared with other projects and containers. This request authorizes removing the release run's local images, not wiping the daemon. Safety skips can legitimately leave references/content behind; report that limit instead of forcing deletion. Free-space recovery is not guaranteed because shared layers/build caches are deliberately preserved.
- The expected nonzero remote-cleanup result must not suppress local finalization after successful publication. Conversely, local removal failure must never cause republishing or be confused with failure of the already verified remote release.
- New live publication changes `latest` and release history; reconfirm the version/target before executing. Existing `v0.2.3` remains historical, with no implied permission to edit its description or source tag.
