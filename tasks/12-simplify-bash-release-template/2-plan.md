## Scope

Implement task 12's new goal, not task 11's narrower convenience wrapper. Make `./scripts/release.sh` a genuine Bash-first build-and-publication entry point, with a root `Dockerfile` and a few supporting files under `scripts/`. The default path must not invoke Python, Node, the managed updater, or `release_template/`. Use the inspected `~/workdir/home-web/scripts/release.sh` as a simplicity reference, not as code to copy wholesale; the literal reference path in the request does not exist.

Support one container image, `linux/amd64` and `linux/arm64`, one versioned Git tag/Gitea release, project-focused Markdown notes, and the registry `latest` alias. Keep the existing image name `git.lan/dev/container-release-template-hello` in this project's explicit configuration; never borrow home-web's target or credentials. Adopt the template elsewhere by copying the small Bash files and configuring that consumer deliberately. No installation into another project, live release, source push, tag push, package reassignment, credential access, image deletion, or production probe is authorized during implementation.

Do not recreate every Python-engine capability in shell. Preserve the existing Python code, examples, historical notes, archived evidence, and checkpoints as legacy material rather than deleting them. The new default does not offer suites, arbitrary build hooks, image archives, release attachments, automatic package linking, remote retention, local image removal, or old-checkpoint adoption. Publication success must no longer automatically enter a cleanup workflow. This intentionally changes the supported default workflow and warrants version 0.3.0.

## Implementation Plan

### 1. Define the small Bash template

- Replace the thin default wrapper with a Bash entry point supporting only no arguments, `--validate`, and `--help`. No arguments means build and publish; unknown options fail before credentials or external effects. Resolve the project root from the script location so invoking it from another directory is unambiguous.
- Add `scripts/release.json` as the only release settings file. Use strict JSON processed by `jq`, never `source`, `eval`, or dynamically constructed shell commands. Define schema 1 fields for HTTPS Gitea origin, exact `owner/repository`, full registry image, login, token-file path, relative notes path, and the two-platform list. Read the version from root `VERSION`; derive `v<version>` automatically. Do not add redundant version/tag settings, arbitrary command strings, or an inline secret field.
- Configure this repository explicitly for its existing Gitea origin/repository/image and login `dev`, using the protected token-file default `~/.config/git/token`. This file is public configuration, not authority to publish during implementation. Document changing these values before copying the template elsewhere. Preserve `GIT_TOKEN` as an optional token-file-path override and `GIT_USERNAME` as an optional login override, without requiring either for the configured default.
- Add a root `Dockerfile` based on the current Ubuntu Hello World fixture, with default output `Hello World` and no embedded credentials. Set OCI version/source/revision labels during the build. Add a root `.dockerignore` excluding `.git`, local state, credentials, task records, and other irrelevant context. The standard build context is the captured committed root; consumers customize the Dockerfile rather than selecting a hook framework.
- Keep supporting responsibilities cohesive: `scripts/release-common.sh` for validation, bounded/redacted command errors, HTTP/registry helpers, and lock/auth lifecycle; `scripts/release-identity.jq` for the small new identity validator/serializer. Do not scatter the linear publication sequence across many files or implement a generic plugin system.

### 2. Validate source configuration and credentials

- Implement `--validate` as local configuration/version/path validation only: no credential-file read, Docker invocation, Git network request, or mutation. `--help` must work without release dependencies. Runtime prerequisites are Bash, Git, Docker Buildx, curl, jq, SHA-256 utilities, `flock`, and standard Linux/POSIX tools; require no privileged installation.
- Validate exact schema/field types, a strict non-leading-zero semantic version, the two unique supported platforms, safe relative regular-file paths, credential-free HTTPS origin, and consistent registry host/owner/image scope. Reject unknown fields and duplicate JSON keys rather than letting `jq` silently select the last duplicate; use a tested `jq --stream` duplicate-key check before ordinary decoding. Restrict supported package/repository names explicitly and reject path traversal, control characters, URL userinfo/query/fragment, and unsafe tag/ref components.
- Require a clean `main` checkout, including untracked files except explicitly ignored run state. Validate both effective fetch and push URLs against the configured repository, accounting for SSH/HTTPS forms and rejecting mismatches. Require remote main to equal the captured HEAD; do not silently push or force source. Capture source, config hash, version, notes bytes/hash, and target once, and recheck source/config before mutation boundaries.
- Load notes from the captured commit as an exact regular UTF-8 blob of at most 64 KiB, with `# Release v<version>` first and project changes below. Use literal tree lookup and object-ID reads, not current-filesystem resolution of historical paths. Normalize only CRLF/CR and trailing newlines; reject malformed bytes and mismatched headings. Retain committed notes separately from machine identity.
- Acquire the existing destination-wide `.template-operation.lock` nonblockingly for the entire mutating run, reject an unfinished `.template-transaction`, and create only explicitly ignored private temporary/run paths. The lock protects this checkout, not all server writers; require operator serialization of releases to the same repository/image.
- Read the private regular, non-symlink token file without printing its bytes, sourcing it, or putting its value in command arguments. Preserve the existing path-override meaning of `GIT_TOKEN`; support the default home path without expanding arbitrary shell text. Use private mode-0600 curl configuration and a minimal temporary Docker auth directory with credential helpers disabled. Preserve the selected Docker context/connection without copying the user's auth inventory. Use traps that clean only run-owned temporary paths, including on failure; never use shell tracing or relay raw credential-bearing HTTP/command failures.
- Check builder support for both platforms before Git network operations, authentication, or builds. Reuse the reference's advertised-capability concept without requiring Node or pretending advertised platforms prove runtime emulation. Keep TLS verification enabled and refuse HTTP redirects for authenticated requests; bound request/command waits and report bounded errors.

### 3. Build and publish one verified image

- Keep publication as a readable sequence: local validation and lock, prerequisites/platform check, source/remote/version checks, predecessor snapshot, staging lookup/build, immutable image verification, exact tag reconciliation, alias promotion, release creation/verification, and success output. Never publish a release before its image is verified.
- Check all paginated non-draft/non-prerelease release and tag evidence before building. Refuse a newer published semantic version, malformed/ambiguous relevant evidence, equal-version conflicts, and a requested immutable tag at another commit. Do not rely on lexicographic version order, a single first page, or a lightweight-tag commit match to adopt an annotation.
- Capture the existing `latest` digest as the predecessor for this invocation. An existing old-format release is historical evidence only: preserve it, and do not claim new-format ownership, retention authority, or old checkpoint compatibility. Require `latest` to remain at the captured predecessor or this invocation's prepared digest before promotion. Fresh version/source checks must also still hold. Explain that this is conflict detection, not an atomic compare-and-swap across independent writers.
- Derive a release-specific staging tag from the version, captured commit, and config hash; use an ordinary single `docker buildx build --platform linux/amd64,linux/arm64 --provenance=false --push` when no recoverable matching staging object exists. Build from a private snapshot of the committed root, not an ignored/local working-tree context. Reject captured archive entries that escape the snapshot. Save/verify Buildx metadata when a build runs and refuse contradictory metadata.
- Resolve the staging index to its immutable digest and verify its complete runnable platform set, member configuration platform fields, and OCI source/revision/version labels. Reuse only evidence matching the captured inputs; an unrelated staging object is a refusal. Promote that exact digest with imagetools rather than a second build, and verify the resulting `latest` digest. Do not create versioned final registry aliases or local export archives by default.
- Define a separate, explicitly marked Bash identity format, `container-release-bash/1`, in a deterministic direct annotated Git tag. Include repository, version/tag, source commit, config hash, template script-content hash, image/digest/platforms, captured predecessor digest, and notes path/hash. Canonicalize with `jq -cS`, use a fixed tagger identity/time, and validate exact regenerated object bytes/ID. New identities must never masquerade as Python schema-2 annotations. Do not place machine identity in the public release body.
- Inspect local and remote tag objects without overwriting local refs; push only the exact expected object with an ordinary non-force push. An existing tag must match its complete annotation and peeled commit. Create the Gitea release using only the committed project notes, expected source tag, and versioned title; do not upload attachments or run package-link POSTs. Confirm its published/non-prerelease state and exact normalized body/tag identity after creation or response-loss reconciliation.
- End with the version, immutable image reference, `latest` reference, and release URL. Exit zero only after tag, immutable image, final alias, and release have been freshly verified. No missing-deletion-evidence error follows a successful Bash publication because cleanup is not part of this path.

### 4. Make partial failures explicit

- Use the release-specific staging tag and immutable annotated tag as recovery evidence, not a new shell checkpoint database. Before the annotated tag exists, a retry may reuse verified staging evidence; after the tag exists, its exact bound digest, notes, source/config/script identity, and predecessor are authoritative. Recreate its deterministic local object if needed without changing identity or local refs.
- If tag intent already exists remotely, require its referenced immutable digest to remain available and verified. Do not rebuild a vanished bound object, refresh its predecessor to a foreign current alias, edit release bodies to hide conflicts, replace a tag, or adopt a receipt from modified scripts/config/source. A retry with newer publication or unrelated alias evidence must stop.
- Lost tag-push/release-POST/promotion responses require fresh remote reads. Complete a matching operation without duplicate confirmed writes; fail on contradictory evidence. Validate returned HTTP status before decoding body; a successful `null`, malformed JSON, authorization failure, timeout, or server error is not absence. Only route-specific expected 404 responses establish absence.
- Without a durable completion journal, a new process cannot distinguish an interrupted tag-only publication from deletion of a previously completed release. On startup, an existing bound tag with a missing release, or an existing release with a missing tag, must stop for explicit operator inspection rather than automatically recreate missing publication records. A currently running process may proceed from its own confirmed new tag to first release creation; a lost release-POST response is reconciled by a matching existing release. Document that some partial runs therefore cannot be resumed automatically with the bare command.
- Do not advertise power-loss durability, automatic cross-revision resume, or exactly-once build execution. With no durable pre-build checkpoint, a process stopped before any recoverable staging result may build again on an explicit rerun; state this limit clearly. Once annotation-bound identity exists, never change the digest to make retry pass.
- Do not roll back remote tags/releases/aliases, delete partial uploads, unlink packages, prune caches, or remove local images in traps or recovery. Leave partial remote objects intact, print the failed phase without secrets, and direct the operator to the same clean source/config for inspection. A published release whose final verification fails must be reported as uncertain/incomplete, not silently deleted or declared successful.

### 5. Keep legacy transactions isolated

- Preserve `release_template/`, `scripts/launch.py`, Python examples/tests, historical notes, archived tasks, and all live checkpoint provenance. Add `scripts/legacy-release.sh` as an explicit wrapper for the existing Python launcher and existing CLI arguments. Keep old transactions on their original immutable checkout/pin; the new wrapper is not permission to reuse new source with old state.
- Reject the new Bash path when managed-installation markers, an in-progress update, or a same-version legacy checkpoint exist. Explain the legacy path rather than guessing between engines. Do not silently reinterpret old `publish --config ... --tag ...` arguments as the new workflow; report the explicit legacy entry point.
- Changing `scripts/release.sh` breaks bootstrap protocol 1's stable-byte requirement. Make `scripts/update.py` clearly refuse installing a Bash-template source revision as a Python managed inventory before any destination write, while retaining installation/verification of old Python revisions. Add a regression for both refusal and an unchanged old-revision installation. No bootstrap migration or new installer is introduced here.
- Adjust installer tests to use a deliberately frozen compatible Python-bootstrap fixture rather than assuming every new HEAD remains an installable legacy revision. Preserve refusal of modified managed files, identity mismatches, concurrent locks, and incomplete transactions. Do not disable the legacy suite or silently update managed checksums to accept changed bootstrap bytes.

## Acceptance Criteria

- After one-time public settings and private token-file setup, `./scripts/release.sh` needs no arguments or inline environment variables to build and publish the configured root Dockerfile.
- The default release path runs Bash and standard external tools plus jq, never Python/Node or the managed installer. A root Dockerfile and a small scripts/configuration set are sufficient to copy into a newly approved consumer.
- The Bash path verifies clean captured source, effective destinations, exact version, both platforms, immutable image configuration, annotated tag identity, and notes-only release body. It builds once per normal attempt and promotes the resulting digest rather than rebuilding for `latest`.
- Wrong or uncertain remote evidence fails closed. Matching retries reuse available staging/tag evidence without changing bound identity or repeating confirmed writes; ambiguous tag-only/release-only states require inspection, and unbound build-retry limits are explicit rather than concealed behind an exactly-once claim.
- Credentials are read from a protected file and remain out of source, arguments, logs, inherited Docker credential stores, and build snapshots. `--validate` and `--help` do not read them or contact services.
- Publication does not perform package reassignment, local/remote deletion, rollback, broad pruning, or source force pushes. A verified Bash publication exits successfully without demanding cleanup evidence.
- Legacy source/checkpoints/history stay intact; new format/default/bootstrap changes cannot silently migrate them. Old managed revisions remain separately usable; the installer refuses unsupported Bash source revisions safely.
- New isolated Bash tests, retained Python tests, syntax/config/version/docs/diff checks pass. No live release, real credential access, foreign project modification, or implementation change occurs during this planning stage.

## Risks And Decisions

- Simplicity comes from narrowing scope, not translating the full Python engine into Bash. Keep a linear single-image flow, a small explicit JSON config, and one jq identity policy; do not add a second general-purpose release framework.
- Bash is the orchestrator, not a JSON parser. jq is an explicit runtime dependency; Python remains a test/legacy dependency only. Duplicate-key detection and strict type/schema handling need focused tests because plain jq decoding alone is insufficient.
- A no-argument command becomes mutating after setup. Make help, local validation, target summary, documentation, and explicit committed configuration clear; do not add an interactive prompt that prevents unattended use. The implementation task itself is not approval to run the live command.
- The home-web reference uses a token-value environment variable, uploads archives, and rebuilds for `latest`. Deliberately do not copy those choices: preserve token-path credentials, notes-only releases, and digest promotion.
- New identity format and changed bootstrap are compatibility breaks. Preserve the legacy implementation instead of destructive removal; old live transactions must stay on their captured pin. There is no automatic transfer of Python retention ownership to Bash releases.
- Cross-service publication is not atomic. A checkout lock and predecessor checks cannot exclude independent writers or roll back an accepted request safely. Require one operator-controlled writer and report partial outcomes honestly.
- No new durable shell journal means some pre-identity interruptions require another build on explicit retry. Do not claim the Python engine's fsync/checkpoint guarantees, support power-loss recovery, or silently rebuild after an immutable annotation has bound the digest.
- Keeping legacy code temporarily means the repository has more than the minimal adoption layout. The default user-facing path must still be small and independent; wholesale legacy removal requires a separately scoped request after migration needs are understood.
