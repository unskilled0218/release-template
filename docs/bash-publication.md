## Sequence

After [setup](bash-configuration.md), run `./scripts/release.sh` from the clean, already-pushed project `main`. The command locks `.template-operation.lock`, rejects managed/incomplete legacy installations and same-version legacy checkpoints, checks advertised platforms, and verifies effective fetch/push destinations and exact remote main. It does not push source for you. One operator must serialize writers to the target repository/image; a checkout lock is not a distributed lock.

Source verification requires exactly one effective push URL from `git remote get-url --push --all origin`, not just a matching first URL. Git expands rewrite rules and uses ordinary remote URLs when no explicit push URL exists. Empty, malformed, failed, or multiple-entry evidence stops publication; duplicate matching entries are also unsupported. The first effective fetch URL remains the read authority and must match the configured target. These checks run again through each source scan; they do not modify remotes or grant permission to write to another repository.

Use the [operator checklist and troubleshooting](release-process.md) before publication. Fixed `Release progress:` milestones appear on stderr before major operations; they do not stream raw build output or secrets. The staging build uses `--push`, so build and staging publication are one operation. Failure guidance distinguishes invocations that sent no publication writes from possible accepted staging/publication writes, without granting repair authority. Existing remote objects may still exist after any early failure.

Before any staging lookup that could build, complete bounded release/tag inventories and classify the requested remote tag/release. For a fresh version, capture `latest` as the predecessor, recover matching release-specific staging evidence or build once into a staging tag from a private committed source snapshot, verify both platform manifests/configuration labels, create/push the exact deterministic annotated tag, promote the verified digest to `latest`, create the notes-only Gitea release, then freshly verify all results. Link the configured package only after publication verification, and recheck publication and association before success. The command does not build image archives or rebuild for promotion. Ignored/untracked worktree secrets are not exported into the committed snapshot; credential files must remain outside the project.

Prerequisite reads have explicit failure branches; they are not evaluated as mutation permission inside a Bash comparison. The final promotion decision validates the same successfully read alias against the captured predecessor and prepared digest. A failed/oversized/malformed read or a newly foreign alias stops before promotion or release creation; an already-prepared alias skips duplicate promotion. No failure refreshes the predecessor or authorizes rollback.

Machine identity uses the `container-release-bash/1` annotation. It binds source, configuration/script hashes, version, image/digest/platforms, predecessor, and notes hash/path. Fixed tagger identity/time and canonical JSON allow exact local reconstruction. Local refs are never overwritten; remote tag pushes are non-force. Existing old-format history is preserved, not adopted as new-format ownership. The removed engine is not required to verify current-format evidence; historical transactions still require their original preserved checkout/pin.

Success prints the version, immutable image, latest alias, and release URL and returns zero. There is no automatic cleanup stage, so missing deletion evidence is not a post-publication failure in this workflow.

## Retry states

If both tag and release are absent, a retry may reuse verified staging. If staging was never recoverably published, an explicit retry may build again; there is no durable pre-build journal or exactly-once guarantee.

If both tag and release exist and match the complete current identity/body, verify the annotation-bound immutable digest and require `latest` to equal it. A missing or foreign staging alias is irrelevant: completed verification makes no staging lookup and performs no build, promotion, tag push, or release POST. A correct package link remains read-only; an explicitly unlinked package may receive the one scoped association POST described below. This is the only completed-retry write exception. Missing bound content, an old/foreign/missing final alias, changed source/config/scripts/notes, or newer publication evidence is a refusal, not repair authority.

Tag-only and release-only startup states are ambiguous and stop before builds or publication writes. Without a durable journal, the script cannot distinguish an interrupted first publication from a deleted completed record. Inspect the same source/config and exact remaining objects; any manual completion requires separate review. Do not delete records, rewrite tags/checkpoints, roll back source, or keep retrying with changed identity to force success.

A running fresh invocation can reconcile its own lost tag/promotion/release response against fresh matching remote evidence without repeating a confirmed write. It may continue from its own newly confirmed tag to first release creation; that in-memory evidence is unavailable to a new process. Byte-budget/input refusals stop, not becoming permission to continue writing after a truncated response. No failure trap performs remote rollback or deletion. Local immutable object recreation is not remote repair.

Tag confirmation is a one-way in-memory transition only after a fresh inventory proves the exact object and peeled source commit. Later promotion/release guards require that same tag to remain present. Disappearance, lightweight replacement, changed annotation, or wrong peeled evidence stops before the next write; it does not grant repush or release auto-tag authority. If promotion already succeeded, a later refusal leaves its accepted alias intact and sends no release POST. Startup ambiguity rules and the absence of a durable journal remain unchanged.

Promotion confirmation is a separate one-way in-memory transition after a successful read proves `latest` equals the prepared digest. It also applies when promotion was skipped or its lost response was reconciled. Before confirmation, the fresh alias guard permits the predecessor or prepared digest; afterward its first read must equal the prepared digest exactly. An observed predecessor reversion, disappearance, foreign digest, or read failure stops before release creation. There is no retry that erases contradictory evidence, predecessor refresh, repromotion, rollback, or deletion.

## Package association

After proving the completed publication, read `GET /api/v1/repos/{owner}/{repo}` and `GET /api/v1/packages/{owner}/container/{name}/latest`. The second endpoint selects the literal published `latest` tag, not the `/-/latest` latest-version selector. Require exact package owner, type, name, version, a positive integer ID, and an explicit `repository` field. Validate repository identity by positive integer ID, full owner/name, name, and owner login; display URLs are not authority. The OCI `org.opencontainers.image.source` label does not replace association verification.

An exact existing association causes no POST. A conflicting association stops without unlinking or reassigning it. An explicit JSON-null association is only a candidate for linking: Gitea also returns null when the caller cannot access an existing linked repository. Before any new link, require `GET /api/v1/version` to return stable `1.25.x` or exact stable `28.2.0`, whose reviewed server-side link service refuses already-linked packages. Other versions, including `28.2.1`, development builds, and suffixes cannot authorize writes. Correct existing links do not need this version check. Missing packages, inaccessible or incompatible APIs, malformed identity evidence, and failed prerequisite reads never authorize a POST. Refresh target and package evidence before one bodyless `POST /api/v1/packages/{owner}/container/{name}/-/link/{repo_name}`, require its empty HTTP 201 response, then read back the exact link. Package names come from the image setting, not the repository name. The link is package-wide and affects all its versions; no other package is enumerated or changed.

A transport failure after dispatch may be reconciled through one fresh package read without repeating the POST. Only a proven exact link allows continuation. Input/resource/HTTP-status refusals are fatal, not reconciliation authority. Publication and association are checked again before `Publication verified` is printed. A failure returns nonzero and preserves accepted image, tag, release, and link state; no unlink, deletion, or rollback is attempted. An explicit retry with the same source/version may complete an unlinked package only after all completed-publication checks pass. Updated script hashes cannot adopt publications made by old scripts.

The API has no documented atomic compare-and-set for association. Operator-enforced exclusion must cover other association writers, UI actions, and in-flight requests until completion. Even the server-side existing-link check is not an atomic conditional update; a preflight read and the local lock cannot guarantee safety against concurrent external changes. Do not run association writes without this prerequisite. Contract references: Gitea v1.25.0 [`package.go` routes](https://github.com/go-gitea/gitea/blob/v1.25.0/routers/api/v1/packages/package.go), [`Package` response fields](https://github.com/go-gitea/gitea/blob/v1.25.0/modules/structs/package.go), [permission-filtered package conversion](https://github.com/go-gitea/gitea/blob/v1.25.0/services/convert/package.go), and [existing-link refusal](https://github.com/go-gitea/gitea/blob/v1.25.0/services/packages/package_update.go). Supporting another version family requires reviewing its refusal semantics first, not relaxing the version check blindly. No live API or Packages-tab rendering is certified by local tests.

The additional exact `28.2.0` contract was reviewed at upstream commit `829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1`, resolved from annotated tag `v28.2.0` (tag object `1dc1ecdddcdc60ab14ec14e30e7bb4d84242f21f`). Permanent references: [route registration and access middleware](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/routers/api/v1/api.go), [package GET/link handler](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/routers/api/v1/packages/package.go), [response fields](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/modules/structs/package.go), [repository identity conversion](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/convert/repository.go), [permission-hidden null conversion](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/convert/package.go), [existing-link refusal and target package-unit write check](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/services/packages/package_update.go), and [non-conditional database link update](https://github.com/go-gitea/gitea/blob/829b49c1ae96015e345f9d2a0eb1ea7acd5f31e1/models/packages/package.go). The link handler returns HTTP 400 for an existing link, HTTP 403 for denied permission, and empty HTTP 201 on success. The API also requires package read/write access and appropriate token scopes; the service requires matching owners and target repository package-unit write permission. The response's positive `id` identifies the package version, while association is package-wide. These source checks do not establish the deployed binary's provenance or permissions.

For downstream compatibility changes, resolve the exact upstream tag to a commit, review routes/access, identity fields, hidden-link behavior, refusal semantics, and database concurrency guarantees, then extend the narrow version check only for the reviewed contract. Run helper and full-entry association regressions for old and new contracts, including unsupported-version boundaries. Do not treat a version string or a fake-server success as live certification. An approved disposable deployment experiment needs explicit target/source/version, repository/package scope, credentials/permissions, and writer exclusion; local verification does not authorize it.

If the version gate refuses a new link, inspect the already-accepted publication and association read-only before deciding any retry. Keep the original source/config/checkout for historical publications: changed script hashes cannot adopt them. Do not remove the gate, bypass HTTPS trust, unlink/reassign a package, or blindly retry an uncertain write to force success. Review a new contract separately or use an already-reviewed supported deployment for future releases; permission and connectivity failures still require their own diagnosis.

## Resource limits

The standard-library helper caps each Gitea response/OCI manifest/index at 4 MiB, OCI configuration/token responses at 1 MiB, notes and annotations at 64 KiB, and ref advertisements at 16 MiB. HTTP headers are capped at 64 KiB, status at 16 bytes, and stderr at 1 MiB without raw output relay. Data is bounded while receiving, before JSON parsing. Valid complete exact-limit bodies are accepted; one byte over is refused, never parsed as a prefix.

Each inventory scan shares limits of 1,002 API pages, 100,000 API/ref records, 64 MiB cumulative payload, and 600 seconds. API pages request 100 records and each listing must end with a confirmed empty page. Repeated pages/duplicate identities, exhausted budgets, or missing termination are incomplete evidence and block the next write. Individual reads time out after 60 seconds; a build has a separate 7,200-second timeout. These limits bound decoded helper output, not Docker build storage or arbitrary Git pack transfer size.

## Limits of authority

The workflow supports one image, two platforms, and association of that image's package with the configured repository, not arbitrary hooks, suites, archive attachments, managed upgrades, automatic tests of consumer applications, retention, local-image removal, or old-checkpoint migration. Run application tests separately before committing/pushing the release source. Only explicit null association evidence on a supported server can permit a link attempt; observed conflicts and server-side hidden-link refusals preserve the original association under the exclusive-writer prerequisite above.

Fresh version/source/alias checks detect conflicts but cannot make cross-service operations atomic or exclude writers in other checkouts. Keep operational writer exclusion and unchanged checkout configuration through completion. No live 0.6.2 publication, Packages-tab rendering, runtime/emulation result, power-loss durability, storage behavior, or deletion safety follows from local fake-port tests. Earlier v0.2.5 live results remain historical.
